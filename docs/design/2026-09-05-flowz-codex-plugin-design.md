# FlowZ Codex 插件版设计

生成日期：2026-09-05
状态：APPROVED（2026-09-05）
目标分支：`main`
保留分支：`FlowZ-Cline`

## 1. 设计目标

将普通 FlowZ 的 `main` 改造成一个同时适配 Codex CLI 和 ChatGPT 桌面版 Codex 的本地插件。FlowZ 的职责不是重新实现 Codex 的 Plan，也不是接管用户已有的工作流，而是主动决定何时以及如何使用宿主 Plan，并为长任务提供清晰的边界、验证和恢复契约。

FlowZ 是一个策略与编排层：

```text
用户任务
  -> FlowZ 判断任务深度、风险和已有工作流
  -> 决定是否使用宿主 Plan，以及需要的推理投入
  -> Codex 原生 Plan 或用户已有工作流完成具体规划
  -> FlowZ 维护批准边界、连续执行、验证和报告
```

FlowZ 应该主动工作，但不应改变用户的项目规则、配置或第三方能力。

## 2. 范围与非目标

### 范围

- Codex CLI 和 ChatGPT 桌面版 Codex 的 Skills + Hook 插件；
- 本地/个人 marketplace 安装；
- 完整插件元数据：作者 `JayPaiZ`、MIT 许可证、仓库和主页、描述、品牌色以及图标字段；
- Quick / Standard / Full 任务分流；
- 宿主 Plan 优先、结构化契约兜底；
- 推理策略与 Plan 路由协作；
- 对用户已有 `AGENTS.md`、Skill、插件和工作流的冲突保护；
- 长任务连续执行、压缩后恢复和必要时暂停；
- 第三方 Skill 首次依赖准备与 GitHub 回退；
- ChatGPT 网页版辅助和用户验证建议两个可独立关闭的开关；
- 完整原图与透明圆形小图标资产。

### 非目标

- 不替代或复制 Codex 原生 Plan；
- 不要求或捆绑 Superpowers；
- 不修改用户或项目的 `AGENTS.md`、Skill、插件或 `config.toml`；
- 不把 FlowZ 规则写入用户项目目录；
- 不提供 MCP、自定义 UI 或 IDE 专用适配；
- 不提交公共插件目录；
- 不在 `main` 保留 Cline 专用运行时文件或面向领导的 PDF 使用说明。

## 3. 核心路由策略

### 3.1 任务分流

FlowZ 读取适用的项目规则、当前已加载的 Skill/插件和必要的项目证据后，选择最小可行层级：

| 层级 | FlowZ 行为 | Plan 行为 | 批准与执行 |
| --- | --- | --- | --- |
| Quick | 识别低风险、小范围任务，直接执行并验证 | 不使用 Plan | 意图清晰即可开始 |
| Standard | 判断是否存在明显不确定性、方案选择或局部边界变化 | 有需要时使用宿主 Plan；无宿主能力时使用紧凑结构化契约 | 只有实质行为、数据、权限、架构或外部状态变化才等待批准 |
| Full | 主动建立完整设计、风险和执行边界 | 优先使用宿主 Plan；没有时使用 FlowZ 结构化设计 | 先取得设计和范围批准，再在边界内连续执行 |

FlowZ 可以主动选择 Plan 路由，但不会要求用户学习某个固定命令。宿主入口由适配层按当前 CLI/桌面版能力决定；如果入口不可用，必须保持相同的设计字段和批准语义。

### 3.2 Plan 上下文包

FlowZ 传给宿主 Plan 或结构化兜底流程的内容保持紧凑，包含：

```text
目标
范围与非目标
已知约束
相关文件和证据
已确认决策
方案与取舍
验收标准
验证方式
批准后可自主执行的边界
需要暂停的条件
```

Plan 获得批准后进入连续执行状态。只有以下情况重新规划或请求确认：

- 新证据推翻当前方案；
- 需要越过已批准范围；
- 涉及破坏性操作、权限变化或未授权外部状态；
- 环境阻塞且无法在原边界内恢复；
- 用户已有规则明确要求暂停。

普通实施阶段、普通验证和长任务的中间进度不触发重复批准。

### 3.3 推理策略

推理是 Plan 使用策略的一部分，而不是一个必须单独安装的 FlowZ Skill。

- FlowZ 根据任务层级和不确定性判断所需的分析深度；
- 可向宿主传递“需要更深入推理”的任务要求或建议；
- 不暗中更改用户选择的模型、推理档位或 `config.toml`；
- 用户已加载的推理 Skill 或等价工作流优先；
- 只要求可审阅的假设、证据、取舍和结论，不要求输出完整内部思维过程。

## 4. 用户工作流冲突保护

### 4.1 优先级

FlowZ 遵循宿主实际优先级，不宣称能够绕过更高层约束。对 FlowZ 自身的路由而言，优先级为：

```text
宿主/系统安全边界
  > 用户和项目已有规则、AGENTS.md、已启用工作流
  > 当前任务中的明确选择
  > FlowZ 默认策略
```

用户可以明确暂停 FlowZ、跳过 FlowZ 的 Plan 或选择自己的流程，但不能借此绕过宿主安全策略或项目硬性规则。

### 4.2 冲突处理

检查的冲突类别包括：Plan/审批阶段、任务深度、验证责任、文件范围、Skill/插件命名、外部操作和权限要求。

发生冲突时：

1. 不修改冲突来源；
2. 跳过冲突的 FlowZ 行为；
3. 继续执行不冲突的部分；
4. 报告冲突来源、被跳过的行为和可选建议；
5. 同一任务中的相同冲突只报告一次。

无法确定是否冲突时，默认不覆盖已有规则，并记录为待确认项。
冲突标识固定为 `<source-locator>:<rule-slug>`，使用稳定来源定位和小写规则短名，
不包含易变行号或阶段编号；同一来源/动作组合必须复用同一标识。

### 4.3 Superpowers 和其他等价工作流

FlowZ 不依赖、安装或复制 Superpowers。只有当 Superpowers 或其他等价工作流已经在当前会话中明确加载并生效时，FlowZ 才将其视为已有主导流程。仅存在安装目录、可以安装或出现在仓库中，不算已启用。

已有工作流生效时：

- 由已有工作流负责自己的设计、Plan、审批和生命周期；
- FlowZ 不启动第二套同类流程；
- FlowZ 只保留冲突保护、上下文整理、验证底线和会话开关；
- FlowZ 不调用或复刻任何 Superpowers Skill。

## 5. 插件结构与职责

首版采用 Skills + Hook 插件，不加入 MCP 或自定义 UI：

```text
FlowZ/
├─ README.md
├─ AGENTS.md
├─ .agents/plugins/marketplace.json
└─ plugins/flowz/
   ├─ .codex-plugin/plugin.json
   ├─ skills/
   │  ├─ flowz-workflow/
   │  │  └─ references/runtime-state.md
   │  └─ flowz-onboarding/
   │     └─ references/third-party-skills.json
   ├─ hooks/hooks.json
   └─ assets/
      ├─ logo.png
      └─ icon.png
```

### 5.1 `flowz-workflow`

负责运行时工作流：

- Quick / Standard / Full 分流；
- Plan 使用策略和上下文包；
- 推理投入协调；
- 冲突保护与一次性报告；
- 批准边界、连续执行和验证；
- 会话暂停/恢复；
- ChatGPT 网页版辅助和用户验证建议开关。

它不复制第三方 Skill，也不将 Superpowers 作为依赖。

### 5.2 `flowz-onboarding`

负责首次实际任务中的依赖准备和诊断：

- 检查规范 Skill 名和兼容旧别名；
- 优先使用 Codex 原生 Skill Installer；
- 原生安装失败后，从记录的原作者 GitHub 仓库和路径回退安装；
- 路径变更时只在原作者或原仓库内寻找；
- 找到 Fork 或同名替代品时不自动换源；
- 最终失败只报告，不阻断 FlowZ 核心能力；
- 用户明确要求时支持手动重试或查看诊断。

“手动重试或诊断”表示不会在每一轮任务中反复安装；只有用户明确提出重试时才再次安装，查看诊断只展示已保存结果，不重新检查或安装。

### 5.3 Hook

- `SessionStart`：注入一次紧凑的 FlowZ 核心路由和会话状态；
- `UserPromptSubmit`：处理暂停/恢复/功能开关，并触发启用状态下的任务分流；
- `Stop`：只解析 FlowZ 输出的紧凑状态标记，保存可审阅的任务状态；
- `SessionEnd`：清理会话状态；
- Hook 只做确定性的生命周期工作，不把用户提示全文写入持久状态；
- 首次使用需要遵从宿主的 Hook 审核和信任机制。

## 6. 会话状态与开关

状态保存在插件自身的会话数据中，按 `session_id` 隔离，最少包含：

- `flowz_enabled`；
- `chatgpt_web_assist_enabled`；
- `user_validation_enabled`；
- onboarding 检查状态和暂停期间排队的一次重试；
- 当前任务层级和 Plan 阶段；
- 紧凑任务包；
- 已报告的冲突标识。

Hook 不直接持久化 `UserPromptSubmit` 的原始提示或 `Stop` 收到的完整答复；持久状态只能来自标记中的白名单、限长字段。`flowz-workflow` 和 `flowz-onboarding` 不得把原始提示、隐藏推理、凭据或无关项目内容放入标记，Hook 另行过滤明显的凭据形态。Hook 无法仅凭字符串可靠判断一段合法摘要是否在语义上复述了输入，因此这一隐私边界同时依赖 Skill 契约和 Hook 的结构化防护。压缩后恢复这些状态，`SessionEnd` 后清理。

任务状态由 `flowz-workflow` 在可见答复绝对末尾顶格追加唯一的单行 JSON 标记，`Stop` Hook
要求标记带有当前轮换 nonce，只保存白名单字段，不保存完整答复。正文、代码块、重复、
缺少或使用过期 nonce 的标记都会被忽略。标记只能包含用户可审阅的摘要，不能更改插件
开关、schema 版本或注入隐藏推理；非法字段和值会被忽略。这样既不要求 Hook 推测
Agent 的内部判断，也能让 `SessionStart` 在压缩后恢复已批准边界和一次性冲突记录。
冲突记录在同一任务内只能追加，空数组不能清除；只有下一项实际任务开始或会话结束时重置。

### 6.1 全局插件开关

由 Codex 宿主管理。新聊天或新 CLI session 才保证完整启用/禁用效果；不承诺已运行会话中途热加载或卸载。插件关闭后不向用户项目留下规则残留。

### 6.2 会话软开关

- “暂停 FlowZ”：从下一轮用户消息起停止 FlowZ 路由和辅助；
- “恢复 FlowZ”：从下一轮用户消息起重新启用；
- “打开/关闭 ChatGPT 网页版辅助”：只影响该功能；
- “打开/关闭用户验证建议”：只影响该功能。

FlowZ 暂停期间提出的第三方 Skill 重试会排队，并在用户明确恢复 FlowZ 后执行一次；
查看诊断始终只展示已保存结果。

ChatGPT 网页版辅助和用户验证建议默认关闭。用户验证建议关闭时，Agent 仍负责所有可执行的普通验证；开启后也不能转移安全、数据完整性和关键回归验证责任。

## 7. 第三方 Skill 依赖

FlowZ 不复制第三方 Skill，不把它们改名为 `flowz-*`，也不把它们声明为 FlowZ 所有。首版依赖目录记录规范名称、兼容别名、原作者仓库和安装路径：

| 功能 | 规范名称 | 兼容旧别名 | 来源 |
| --- | --- | --- | --- |
| 中文文本处理 | `humanizer-zh` | — | `op7418/Humanizer-zh` 的 `SKILL.md` |
| 英文文本处理 | `humanizer` | `humanizer-en` | `blader/humanizer` 的 `SKILL.md` |
| 方案质询 | `grilling` | — | `mattpocock/skills` 的 `skills/productivity/grilling` |
| 产品构思 | `gstack-openclaw-office-hours` | `office-hours` | `garrytan/gstack` 的 `openclaw/skills/gstack-openclaw-office-hours` |

已安装规范名或兼容别名都视为满足依赖；不覆盖用户已有版本。中文和英文 Humanizer
继续严格分开：双语内容按清晰段落/片段分配，同一混合段落不能同时交给两个 Skill；
用户在同一请求中显式指定两者时，只询问一次分别处理还是仅选一个，再等待回答。
第三方 Skill 缺失时 FlowZ 核心仍可运行。

## 8. 图标与品牌资产

- `logo.png`：保留用户提供的完整水墨图；
- `icon.png`：方形 PNG 画布，主体为透明角的圆形裁切，适配圆形插件展示；
- 圆形版不加边框、不重绘主体，缩小时优先保证人物主体清晰；
- `plugin.json` 从一开始填写完整作者、许可证、仓库、主页、描述、品牌色和图标字段；
- 当前只用于本地 marketplace，未来公开发布前另行确认图像版权和发布方式。

## 9. 错误处理与降级

| 情况 | 处理 |
| --- | --- |
| 宿主没有原生 Plan | 使用同字段结构化设计契约 |
| 用户已有流程冲突 | 跳过冲突项，继续不冲突部分并报告 |
| 第三方 Skill 缺失 | 先安装；失败后报告，FlowZ 核心继续 |
| GitHub 回退失败 | 记录失败原因和下一步，不循环重试 |
| Hook 或状态异常 | 恢复到最小 FlowZ 路由，避免阻塞用户任务 |
| 权限/网络/环境不足 | 保留证据，停止需要该能力的动作，报告可恢复步骤 |
| 新证据超出批准边界 | 暂停并重新规划，不擅自扩大范围 |

任何失败报告都只携带新增证据、失败点、已排除原因和下一步，避免重复完整上下文。

## 10. 安全与隐私边界

- 不读取或输出凭据、`.env`、私有日志和无关运行数据；
- 不向项目写入 FlowZ 规则或隐藏状态；
- 不修改 `config.toml`；
- 不覆盖用户已有规则、Skill 或插件；
- 第三方安装只使用记录的规范来源，不自动替换为 Fork 或同名项目；
- 外部操作保持最小化并遵从宿主权限和审核；
- 插件禁用或会话暂停后，不通过残留项目文件继续生效。

## 11. 从当前 Cline 基线迁移

- `FlowZ-Cline` 分支保留当前 Cline 版本和已完成的安装器、规则与文档；
- `main` 迁移为 Codex 插件版；
- 删除 `main` 中仅服务 Cline 的运行时规则、安装器和旧 Cline 包装结构；
- 删除 `main` 中的 `使用说明.pdf`，只保留并改写 `README.md`；
- 根目录 `AGENTS.md` 仍仅用于 FlowZ 仓库开发，不安装到用户环境；
- 不向新的 `JayPaiZ/FlowZ` 远程仓库自动推送；
- 后续完成本阶段后，再由用户从开发完成的 `main` 创建 `FlowZ-Codex` 分支；本阶段不提前创建或发布它。

## 12. 验收标准

实现完成后，至少满足：

1. `plugin.json`、marketplace 条目、两个 Skill、Hook 和资源目录通过当前 Codex 插件结构校验；
2. Quick / Standard / Full 路由在有无原生 Plan 时都能得到可执行结果；
3. Plan、推理、批准边界和长任务状态不会与已有工作流重复或互相覆盖；
4. 冲突测试确认用户已有规则不被修改，冲突只报告一次；
5. 暂停/恢复和两个功能开关从下一轮消息起生效，并在压缩后恢复；
6. 第三方依赖按规范名/别名识别，原生安装失败可按原作者 GitHub 来源回退；
7. 任一第三方依赖失败不会阻止 FlowZ 核心流程；
8. ChatGPT 网页版辅助和用户验证建议默认关闭；
9. 中文和英文 Humanizer 不会被交叉调用；
10. 图标包含完整原图和透明圆形派生图，manifest 引用正确；
11. `main` 不再依赖 Cline 专用文件或 PDF，`FlowZ-Cline` 分支仍可独立保留原基线；
12. README 清楚说明安装、开关、Plan 路由、冲突保护、依赖回退和隐私边界。

## 13. 实施顺序（仅设计层面的建议）

1. 创建并校验插件骨架、元数据、marketplace 条目和图标资源；
2. 编写 `flowz-workflow` 的路由、Plan/推理策略、冲突保护和状态契约；
3. 编写 `flowz-onboarding` 的依赖目录、安装回退和诊断契约；
4. 添加 Hook，并用模拟会话验证下一轮开关、压缩恢复和失败降级；
5. 更新 README，移除 `main` 的 Cline/PDF 内容；
6. 运行结构、静态、行为、资源和范围验证，检查最终差异；
7. 由用户在本地 marketplace 安装并进行一次 CLI/桌面版验收。

## 14. 待实现时核实的宿主细节

这些细节不改变本设计的行为契约，实施时按当前 Codex 版本验证：

- CLI 与桌面版的插件安装入口和 marketplace 本地注册格式；
- Hook 的实际输入/输出字段、会话数据目录和审核提示；
- 宿主 Plan 能力的可检测信号和调用入口；
- Skill Installer 的可调用方式及 GitHub 路径参数；
- 图标字段支持的文件格式、尺寸和展示限制。

若宿主能力与文档或预期不同，优先保留本设计的冲突保护、路由、状态和降级语义，并记录适配差异。
